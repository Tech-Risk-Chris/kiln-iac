# M4 plan: stacks and contexts

**Status: agreed 17 November 2026; nothing built yet.** All open questions below
are settled. Start with step 0 (the synthetic corpus), then step 1.

**Gate (from [ROADMAP.md](../ROADMAP.md)):** a Terragrunt repository with three
environments is replaced and its directory tree deleted.

## What M4 has to buy

Until now one `.kiln` file is one stack, built in one implicit context. Real
repositories have many state files across several environments, with values that
differ per environment and outputs that flow between state files. Terragrunt covers
that with a directory tree, `include` chains, `dependency` blocks and `mock_outputs`.
M4 replaces all of it with values the compiler can check:

1. **Environments as data.** A context is a value, `:extends` is explicit, and
   `kiln why` says where a value came from.
2. **Missing context keys fail at build time**, naming the stack and the context,
   instead of at plan time in one environment.
3. **Cross-stack references are typed.** The type of the upstream stack's return
   value is the mock; no `mock_outputs`.
4. **Run order is data** (`out/graph.json`), so the same repository drives a local
   run, GitLab, or a Makefile.

## Starting point

Neither `defstack`, `defcontext` nor `deploy` exists yet in `src/` or
`src/prelude.kiln`; only `defcomponent` does. `kiln build` takes one file and
writes `out/main.tf.json` and `kiln.lock` beside it. `kiln.lock` is per file
(`version: 1`: addresses, moved, pending). DESIGN.md says `defstack`, `defcontext`
and `deploy` should themselves be library macros, with the compiler providing only
what macros cannot: evaluating a stack once per context, and the cross-stack
graph. Step 2 should check how far that holds.

## Design

### Contexts

```clojure
(defcontext base {:prefix "acme" :region "europe-west3"})
(defcontext dev  :extends base {:env "dev"  :project "acme-dev"})
```

- A context is a map value. A child overrides whole keys; deep merging only where
  the source calls `merge-deep`.
- `(:pools base)` works, so a child can compute from its parent.
- Multiple parents (`:extends [region env]`): a key defined by two parents with
  different values is an error at the child (new code, K08xx) until the child sets
  it. Same value from both is fine. Resolution is by explicit override only, never
  by parent order.
- Contexts are evaluated at build time and are pure, like everything else.
- `kiln why <ctx> <key>` prints the chain of definitions that produced the value,
  with source positions.

### Stacks

```clojure
(defstack network [ctx] {:vpc (g/compute_network "main" {...})})
```

- A stack is a function of one context, evaluated once per context in a `deploy`.
  The return value is the stack's public surface: what other stacks may `ref`.
- Components still flatten into the stack; addresses are unchanged
  (`google_compute_network.main`), and are unique per state file, so two stacks
  may use the same logical name.
- Stack-level inference sees `ctx` as a row-polymorphic record. The keys read from
  it are the stack's requirement (step 3).

### Deploy and layout

```clojure
(deploy [network gke] :in [dev prod] :backend (fn [stack ctx] ...))
```

Output tree: `out/<context>/<stack>/main.tf.json` plus `out/graph.json`. The
`kiln.lock` question is open (see below). Single-stack files with no `deploy`
keep building to `out/main.tf.json` exactly as today, so existing examples do not
move.

### Cross-stack `ref`

`(ref network)` inside stack `gke`, context `dev`:

- adds a `terraform_remote_state` data source to `gke`, with the backend config
  `deploy` gives `network` in `dev`;
- adds exactly the outputs `gke` reads (reads found by inference, so also in
  branches that do not run) to `network`'s `output` blocks, marked `sensitive`
  where the source is secret;
- records the edge `network -> gke` in `graph.json`;
- types the result from `network`'s return value, with every field deferred, and
  secrecy carried over, so M3's stage and secrecy checks apply across the stack
  boundary unchanged.

Cycles between stacks are an error naming the cycle. A `ref` to a stack that is not
in the same `deploy` and context is an error.

### Project file

`project.kiln` at the repository root is the entry point for everything that spans
more than one file. It is one `(project ...)` form, read as data and never
evaluated, so tools can read it without running any Kiln code. Commands find it by
walking up from the current directory, as `cargo` finds `Cargo.toml`.

```clojure
(project
  :files   ["contexts.kiln" "network.kiln" "gke.kiln" "deploy.kiln"]
  :engine  "tofu"
  :default-context dev
  :protected [prod]          ; apply needs --context and a typed confirmation
  :confirm true)             ; ask before apply; --yes is CLI-only
```

- **`:files`** lists the sources in order. They are read as one program, in that
  order, so there are no forward references and no module system is needed;
  a name defined twice is an error naming both files. This settles the "where
  does source live" question for M4.
- **`:default-context`** is used by `plan`, `build` and `why` when `--context` is
  omitted. It never applies by itself: see below.
- **Policy** (`:protected`, `:confirm`, `:engine`) is read by `kiln run`. A project
  file may make the rules stricter, never looser than the built-in minimum: it
  cannot switch off the saved-plan rule, and `--yes` exists only on the command
  line, so a committed file cannot make apply unattended.
- **Staleness comes for free.** Because the project names every source, `kiln run`
  rebuilds in memory and compares with `out/` before doing anything, and refuses
  on a difference. No separate `build --check` step to forget.
- Single-file builds (`kiln build file.kiln`) keep working with no project file.
  `check.sh` and the examples are unchanged.

### Running

`kiln run plan|apply [--context C] [--only STACK]` walks `graph.json` in
topological order and calls the engine in each `out/<ctx>/<stack>/` directory.
Independent stacks may run concurrently later; v1 is sequential. Diagnostics are
rewritten to source positions only in M5 (`kiln explain`); M4 prints the engine's
output untouched with the stack and context as a prefix.

`apply` is the first command that applies. Guardrails, with the project file
carrying the policy: `apply` plans first and applies only that saved plan file; a
context in `:protected` (or any context, when there is no `:default-context`)
must be named on the command line, never defaulted; confirmation is asked unless
`--yes` is given on the command line; output that is stale against the sources is
refused; and apply is never part of `check.sh` or the test suite (tests use a fake
engine script that records its arguments).

### CI adapter

`kiln ci gitlab` renders `graph.json` as a GitLab parent pipeline plus one child
pipeline per context, with `needs:` mirroring the edges and `kiln run plan --context
C --only S` as the job. Generated, deterministic, committed like other output.
Apply jobs are manual by default.

## Steps, each landing green

1. **`defcontext` and resolution.** Reader and evaluator support, `:extends` with
   one or several parents, conflict error, `kiln why`. Tests in `tests/m4.rs`
   (e.g. `child_context_overrides_whole_keys`,
   `two_parents_disagreeing_on_a_key_is_an_error_at_the_child`). New codes in
   `src/codes.rs`; bless `ERRORS.md`.
2. **Project file, `defstack`, `deploy` and layout.** Read `project.kiln`, load
   its files in order.  Evaluate a stack per context, emit
   `out/<ctx>/<stack>/main.tf.json`, give each state its own ledger section,
   migrate `version: 1` lock files. Existing examples unchanged. New example
   `examples/stacks` (network + gke over dev and prod, built from the `gke`
   example), committed with output; `golden.rs` covers it.
3. **Context rows.** Infer the keys and shapes each stack reads from `ctx`; a
   context lacking one is an error per (stack, context) with `help:` naming the
   key and the nearest context that has it. Add to the `IDIOMS` list in
   `tests/m3.rs`. Includes errors in branches that a given context does not take.
4. **Typed `ref`.** As designed above. Tests include a secret flowing across stacks
   into a non-sensitive output (K0321 through the boundary), a deferred upstream
   value used in `count` downstream (stage error), and a read of a field the
   upstream stack does not return.
5. **Backends and `graph.json`.** The `:backend` function result becomes the
   `terraform { backend ... }` block and the `remote_state` config. `graph.json`
   is sorted and byte-stable: nodes `{context, stack, dir}`, edges, no absolute
   paths. `kiln graph` prints it.
6. **`kiln run plan`.** Topological walk, engine lookup as in `main.rs`, prefixed
   output, stops at the first failing stack and says which stacks were skipped.
   Downstream plans of an unapplied upstream fail by design (remote state); say
   so in the message rather than hide it.
7. **`kiln run apply`.** Guardrails as decided. Not run by `check.sh`; tested with
   a fake engine only.
8. **GitLab adapter.** Golden test on the generated YAML.
9. **Pruning `moved` blocks.** See open question 5.
10. **The gate.** Convert the synthetic Terragrunt repository (see "Gate corpus")
    by hand (and with `kiln import` for the HCL parts), compare plans per
    environment, delete the tree. Record what `import` and the stack forms could
    not express as follow-ups, not workarounds.

## Gate corpus (synthetic)

`examples/terragrunt-live/` holds a fictional Terragrunt repository in the usual
"live" layout, built before step 1 so it can shape the design. Fixtures only:
projects named `acme-dev`, `acme-staging`, `acme-prod`, never real ones, and
`check.sh` only inits, validates and (when asked) plans it.

- Three environments, each with its own `env.hcl` and `region.hcl`, and a root
  `terragrunt.hcl` that includes a generated backend and provider block.
- At least three stacks per environment (network, gke, a data layer), with
  `dependency` blocks between them and `mock_outputs`.
- Features chosen to be the hard parts, so passing is meaningful: an inheritance
  chain three levels deep, `locals` that compute from parents, one environment
  with an extra stack or a differing value, and one secret output crossing stacks.
- Uses `random`, `local` and `google` resources already in the schema cache, so
  nothing new is fetched.
- Gate check: each environment's Kiln output validates, plans match the Terragrunt
  tree's plans where the engine can run them offline (`random`/`local` parts), and
  the tree is deleted in the final commit of step 10.

Because we write both sides, it can only show that Kiln expresses these patterns,
not that real repositories fit. The roadmap's gate text should say "synthetic"
until a real repository is tried.

## Decisions and open questions

1. ~~Which Terragrunt repository is the gate?~~ Decided 17 November 2026: strictly
   synthetic for now, which keeps us free to shape it. A real client repository
   stays a later check, as it is for M1. See "Gate corpus".
2. ~~Context conflicts~~ Decided 17 November 2026: with several parents, equal
   values (including the same inherited definition reached by two paths) are fine;
   differing values are an error at the child until it names the value it wants,
   either a literal or a read from a named parent, `{:pools (:pools region)}`.
   Every context is a named `defcontext`, so such a path always exists. The error
   lists each parent's value and position, and suggests those reads in `help:`.
   Missing keys are per-context build errors.
3. ~~`kiln run apply` guardrails~~ Decided 17 November 2026: policy lives in
   `project.kiln` (see "Project file"). Built-in floor that a project cannot
   lower: saved plan only, protected contexts named explicitly, `--yes` CLI-only,
   stale output refused, never in tests or `check.sh`.
4. ~~Layout and lock placement~~ Decided 17 November 2026: one lock per output
   directory, `out/<ctx>/<stack>/kiln.lock`, beside the state it describes. It
   keeps single-file stacks working with no change and gives per-environment
   diffs. Single-file builds without `deploy` stay as they are.
5. ~~Pruning `moved`~~ Decided 17 November 2026: an explicit
   `kiln lock --prune-moved` that the user runs once every state has applied the
   move. Automatic pruning, keyed off successful applies recorded by
   `kiln run apply`, can come later if that proves reliable.
6. ~~Where `defstack` source lives~~ Decided 17 November 2026: `project.kiln`
   lists the files, loaded in order as one program. No module system in M4;
   per-file namespaces would be M5 if wanted.
7. ~~Backends and providers per context~~ Decided 17 November 2026: `deploy`'s
   `:backend` plus ordinary `(provider ...)` forms that read `ctx` are enough; no
   Terragrunt-style generated blocks. If the synthetic corpus shows a need, it
   comes back here as a follow-up, not a workaround.
8. ~~Project file details~~ Decided 17 November 2026: the file is `project.kiln`,
   `:files` takes no globs (order is explicit), providers stay where they are.

## Out of scope for M4

`kiln explain` and diagnostic rewriting, the formatter and language server, policy
rules, graph transforms, `kiln test` (all M5). Orchestrator-fed variables instead
of remote state (deferred past v1). Cross-stack `terraform state mv` scripts
(DESIGN.md "Cross-stack moves"): needed once stacks exist, but not for the gate;
add to the roadmap if the chosen repository needs it.
